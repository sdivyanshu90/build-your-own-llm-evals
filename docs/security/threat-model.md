# Threat model

## Assets and trust boundaries

Protected assets include tenant datasets, model outputs, provider credentials,
API keys, evaluation budgets, audit history, result integrity, and service
availability. Trust boundaries exist at the browser/API edge, API/database
boundary, queue/worker boundary, worker/provider boundary, and object-store
boundary. Dataset content, candidate output, retrieved text, tool results,
filenames, archives, and provider responses are untrusted.

## Threats and controls

| Threat | Primary controls | Residual risk |
|---|---|---|
| Authentication bypass | Hashed API keys, server-side pepper, constant-time comparison, expiry/revocation | Stolen live credentials work until revoked |
| Cross-tenant IDOR | Project RBAC, scoped queries, composite foreign keys, PostgreSQL RLS | A database superuser bypasses RLS |
| Secret disclosure | Secret manager injection, `SecretStr`, structural redaction, no secrets in snapshots | Provider request content may itself contain sensitive data |
| SQL injection | SQLAlchemy bound statements, no user SQL predicates | Operational scripts require review |
| XSS | React escaping, semantic text rendering, HTML report escaping, strict API CSP | Browser extensions and compromised dependencies remain |
| CSRF | Bearer keys, no cookie authentication, restricted CORS | A future cookie mode needs anti-CSRF tokens |
| SSRF | HTTPS-only remote provider adapter, DNS/IP validation, private-network denial | DNS rebinding is reduced, not universally eliminated |
| Malicious upload | Byte/record limits, explicit format parsing, content validation, no archive extraction | Parser vulnerabilities require patching and isolation |
| Path traversal | Object keys generated by the platform; filenames are metadata only | Custom storage plugins must preserve this rule |
| Archive bomb | Archives are not accepted by dataset import | Future archive import needs expanded-size limits |
| CSV formula injection | Dangerous leading characters are prefixed with an apostrophe | Some spreadsheet applications have additional dialects |
| Prompt injection | Trust-separated judge prompt, evidence IDs, no judge tools/secrets, adversarial tests | Language-model instruction following cannot be guaranteed |
| Judge data exfiltration | Project data-handling policy, provider warning, redaction, isolated credentials | External providers receive configured content |
| Log leakage | Structured allowlisted events and recursive secret redaction | New log fields require review |
| Denial of service | Upload/response limits, Redis rate limit, pagination, bounded dispatch, timeouts | Distributed attacks need edge/WAF controls |
| Cost abuse | Project budgets, concurrency limits, estimate checks, atomic ledgers, alerts | Provider price changes and ambiguous billing |
| Supply-chain compromise | Exact locks, Dependabot, audit, CodeQL, secret scan, image scan, SBOM | A signed but malicious upstream release |

## Authentication and authorization

Production rejects development header authentication. API keys store a public
prefix and HMAC-SHA-256 digest under an independent pepper. The raw value is
shown only when created. Roles are explicit permission sets; optional key scopes
can only reduce them. Cross-project denials return not-found to avoid resource
enumeration.

PostgreSQL transactions set tenant context for RLS. Foreign keys include tenant
columns for rubrics, judges, pair assignments, runs, comparisons, and slices.
Administrative audit access is separate from normal result access.

## LLM-specific risks

The judge has no platform tools and receives no provider secrets. Candidate
content is line-labelled and delimited as evidence, and the trusted message
explicitly rejects instructions found inside evidence. Judge output must satisfy
a closed schema. Concise justification and evidence are auditable without
collecting hidden reasoning.

Delimiters are not a security proof. High-risk use requires human calibration,
multiple judges, position reversal, abstention, sensitive-field redaction, and
a provider contract compatible with the project’s retention policy.

## Security verification

Automated tests cover cross-project authorization, redaction, API-key
verification, SSRF destinations, malicious judge instructions, CSV formulas,
invalid schemas, oversized uploads, and script-like model outputs rendered as
text. CI runs dependency, source, secret, filesystem, and image scans.

## Incident assumptions

Assume credentials, provider responses, and audit chains may be separately
compromised. Rotate provider keys and API pepper, revoke API keys, stop dispatch,
preserve database/object-store snapshots, export audit hashes, and scope tenant
exposure before restoration. Hash chaining detects editing relative to a trusted
checkpoint; it does not prevent an attacker with database write access from
replacing the entire chain and checkpoint.
